# Applicability-first WordPress.org review rulebook

**Status of this document:** Practical audit instructions, not official WordPress.org policy. Match the current [Detailed Plugin Guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/) and [Common Issues](https://developer.wordpress.org/plugins/wordpress-org/common-issues/) to actual plugin behavior. Source reviewed: 2026-10-11. Technical review concerns below also derive from direct WordPress.org reviewer messages summarized in `reviewer-cases.md`.

## Applicability matrix

| Rule or review family | When to check | Typical evidence | Do not overflag |
|---|---|---|---|
| **#1 + #2 GPL and licensing** | Bundled PHP/JS/CSS/fonts/images/vendor dependencies | LICENSE, composer/package metadata, bundled file copyrights/licenses | Unlicensed does not automatically mean non-GPL; verify specific component and redistribution terms |
| **#4 human-readable code** | Minified/bundled/obfuscated assets, source map references | Public maintained source linked in readme or included; documented build tools | Minified assets are allowed if source is public and maintained |
| **#5 trialware** | Pro/license/trial/quotas/limited local features; demo/sandbox-only modes | Code implements feature locally and denies access based on payment or count | Distinguish true SaaS, separate add-ons, safety controls and legitimate free feature subsets |
| **#6 SaaS** | Paid/third-party processing or a remote licensed service | Substance of server-side work, account requirement, disclosure, service contract | A license endpoint that only unlocks local code is not SaaS |
| **#7 consent / privacy** | Any outbound calls, telemetry, feedback, opt-in, automatic registration | Activation/onboarding/admin/deactivation/network call chains, payload and consent state | Legitimate user-configured SaaS can be allowed; not all URLs are tracked requests |
| **#8 remote executable code/assets** | CDN JavaScript/CSS, remote images/fonts, updaters, plugin downloads, iframe admin | Enqueue/import/fetch, zip sources, remote script injection | Service-backed scripts and GPL-compatible fonts have case-specific exceptions |
| **#9 honesty and reviews** | Review/rating prompts, Trustpilot testimonials, external claims, hidden manipulations | Upsell wording, testimonial sources, manipulation/coercion, misleading endorsements | Merely mentioning a review platform is not a standalone blanket violation |
| **#10 public-facing credits** | `Powered by`, badges and vendor links rendered on visitors' pages | Opt-in default false, independent of functionality | Vendor links in the admin/readme aren't automatically public front-end credits |
| **#11 admin UX** | Dashboard banners, global styles, ads, redirect on activation | Unwanted sitewide nags, global selectors, dismissibility, admin links | Targeted helpful notices are sometimes permissible |
| **#12 readme spam** | Directory text, tags, affiliate links, screenshot copy | Keyword stuffing, >5 tags, undisclosed affiliate links | Legitimate feature description and modest cross-promotion may be okay |
| **#13 bundled WordPress core libraries** | Core jQuery, jQuery UI, PHPMailer etc shipped as redundant copies | Actual dependency and WordPress core equivalent | Distinct non-core plugins/extensions may be bundled if licensing compatible |
| **#16 completeness / readme parity** | Claimed features, screenshots, FAQ, free/Pro promises | Reachable free-code implementation and visible outputs | Explicit separately distributed Pro features should not be presented as free |
| **#17 trademark/copyright** | Plugin name/slug and branded assets or claims | Ownership/permission, deceptive affiliation or title | Descriptive compatibility references can be valid |
| **Block Directory specific** | **Only** single-block plugins specifically for Block Directory | Dedicated single block, minimal editor-only UI, no admin menus | Skip for ordinary plugins with blocks |
| **Excluded: #3 SVN portions, #14, #15, #18** | Never in this source-code skill | — | No SVN checks, version-bump demands or reviewer administrative process findings |

Guideline #2's security/content responsibility and WordPress.org *Common Issues* support the technical checks below. Cite technical documentation precisely; do not assign a fabricated numbered guideline to a technical item.

## 1. Trialware, actual implementation and freemium boundaries

Trace from UI controls and feature definitions through REST/AJAX/option save, rules engines, renderers, templates, and post-processing. Search `is_pro`, `license`, `activate_license`, `plan`, `upgrade`, `trial`, `quota`, `limit`, `free_*`, capability flags, hard-coded `max`, per-kind counts, disabled buttons, license-dependent conditionals and feature registries. Specifically examine hidden functionality included locally but inaccessible to free users: rules conditions, calculation modes, PDF watermarks, tax columns, campaign types, popups, scheduling, shipping carriers, order bumps, etc. Unreachable/unused code alone is not automatically a lock: demonstrate gating and expected functionality. Verify after removing a license, after trial expiry and at quota threshold in a disposable environment.

**Safe remediation:** either expose all included local functionality without a license or remove the locked local implementation from the WordPress.org package and provide optional code in a **separate** externally distributed add-on. Keep the free plugin useful; remove false readme claims. For genuine SaaS, show processing actually occurs on servers and document service, account, terms/privacy. Do not suggest bypassing licensing or faking a service to evade review.

Inspect support validators and renderer limits together: rejecting multi-step campaigns or slicing saved steps to one can restrict an included engine even without an explicit license check. Establish what the shipped engine actually supports and why the restriction exists before confirming #5; a loop alone does not establish a complete locked feature.

## 2. Remote calls, telemetry, consent and disclosure

Inventory outbound requests from **PHP AND JS**, including `wp_remote_*`, `WP_Http`, `file_get_contents('https://')`, curl, `fetch`, `axios`, `XMLHttpRequest`, `sendBeacon`, iframe/script/link src, CSS `@import`/`url`, minified builds and source maps. Map dynamic endpoints and constants to actual hosts; identify trigger (activation, every admin request, onboarding, cron, support click, checkout, frontend view, deactivation), payload (admin name/email, site/home URL, plugin/theme inventory, IP/country, WooCommerce orders/cart, uploaded files, license data), default consent and ability to opt out without breaking unrelated features.

For **each actual external service**, document in `readme.txt` an `External services` section with name/operator, purpose, when invoked, exact categories of transmitted data, whether an account is required, and direct applicable terms/privacy links. WordPress.org reviewer emails explicitly request both legal links; official guideline #6 words this more flexibly, but the skill should flag absent links as a **reviewer-observed disclosure concern**, not misquote the numbered rule. Verify links when possible. Distinguish optional user-initiated support sends from automated telemetry; still document the support service and explain submitted attachments.

Tracking/marketing/diagnostic telemetry must be truly optional, **off by default**, with an explicit separate opt-in checked on every send path. Admin Google Analytics tracking was specifically rejected in reviewer emails; request removal, not a perfunctory consent checkbox. Determine whether IPinfo and other lookup calls transmit a site IP automatically. Avoid assuming that a request to a legitimate shipping or CAPTCHA API is illegal: validate configuration, processing function, data, docs and user consent context.

Remote static JS/CSS assets (e.g. jsDelivr Driver.js, unpkg react-scan) are typically to be bundled locally or replaced with WordPress core copies. Review copyright and GPL-compatible font allowance separately. Do not fetch/update/execute third-party code as a remedy. Flag remote premium installers/update sources and arbitrary downloaded executable code.

## 3. REST, AJAX, permissions, input and output security

For **every** `register_rest_route` and `wp_register_ability`, inspect `permission_callback` and actual callback operations. Public `__return_true` is acceptable for genuinely public information. For private settings, coupons, user filters, orders, admin changes or filesystem writes, require operation-appropriate capabilities. `manage_options` does **not** replace `install_plugins`, `activate_plugins`, `update_plugins`, `delete_plugins`, or object-level `edit_post`/`edit_user` as needed. Include nonce/CSRF protection for state-changing browser actions; note that **nonces are not authorization**. AJAX endpoints must be audited separately (`wp_ajax_` and `wp_ajax_nopriv_`). Verify fallback/public endpoints cannot reveal sensitive data.

- **Object versus site-wide authority:** post updates/deletions need the relevant `edit_post`/`delete_post` check with the actual ID and intended post-type scope. `manage_options` alone is not a substitute. Conversely, `edit_others_posts` alone does not authorize a site-wide wishlist/settings write; inspect `manage_options` or an intentionally mapped settings capability. Abilities need execution permission checks even when exposed to clients; inspect their actual registration and exposure rather than treating every ability as a REST route.
- **Anonymous analytics writes:** trace client-supplied campaign/interaction IDs to every insert/update. Check target existence and eligibility, event types, field allowlists and whether arbitrary records/counters can be created or changed. Constrain mutation to intended visitor events; use suitable abuse controls where needed. A public nonce is not proof of identity. Requiring admin login for legitimate visitor tracking is not a complete fix. Report demonstrated analytics manipulation separately from private-data exposure.
- **Thank-you/order-received access:** sanitizing an order ID/key does not authorize access. Trace which fields render before an access decision. Verify the supplied key against the selected order for supported guest flows and appropriate ownership/staff authority for other flows. Test correct, absent, wrong and another order's key, plus another customer's ID. Preserve valid guest checkout access.
- **Nonce conditionals:** test missing/invalid nonce and missing capability independently, including flags, alternate actions and fallbacks. Every sensitive branch must reject unauthorized access. A present `check_ajax_referer` call does not prove surrounding boolean logic is sound. Keep request processing inside the intended handler rather than global plugin-load code.

For `$_POST`, `$_GET`, `$_REQUEST`, `$_SERVER`, `$_COOKIE`, `$_SESSION`, `$_FILES`, REST params, JSON and database writes: `wp_unslash()` where appropriate, validate type/shape/allowlists, sanitize at a suitable boundary per field type. Output escaping such as `esc_url()` does not replace input sanitization; inspect request URI processing separately from its eventual URL output. `json_decode()` **does not** sanitize. Review all nested fields and the downstream renderer, not just the raw JSON. Watch for `'validation_callback'` (wrong key) instead of `validate_callback` in REST argument schemas. Password input may need its exact original bytes; do not propose generic stripping for every input. One-time emailed verification tokens have different security needs from admin action nonces.

Escape **late** for HTML text/attributes/URLs (`esc_html`, `esc_attr`, `esc_url`), and use `wp_kses`/`wp_kses_post` with suitable allowlists for intended HTML (such as WooCommerce formatted prices). Evaluate output returned from shortcodes, `the_content` and other filters, not only `echo`. Review unescaped inline JS, SQL injection (`$wpdb->prepare` with placeholders, safe identifiers), stored XSS, upload validation, SSRF and arbitrary file path operations. Avoid labeling `phpcs:ignore` automatically wrong; verify actual behavior.

Include dynamic block `render_callback` returns: titles, term names/links, captions/media, product descriptions and supplied block content. `wpautop()`/`wptexturize()` format content; they are not sanitizers. Inspect `apply_filters()` results at their final sink, including WooCommerce price/quantity/payment messages and plugin video/quick-view hooks. Earlier escaping may precede later filter modifications. Trace custom safe-HTML helpers and `_safe` variables to their implementations, allowed elements/attributes/protocols and subsequent mutations. Suppression comments and claims that core already escaped a value are leads, not evidence. Preserve legitimate rich content and checkout/payment functionality when proposing allowlists. Where a verified helper must return safe generated markup, document its complete escaping contract and the reason final KSES is unsuitable; official escaping guidance allows this narrow case. Avoid blanket re-sanitization of core-rendered content without examining its trust boundary.

### Arbitrary CSS/JS/PHP insertion

The 2026-10-26 WowStore and WowOptin messages request removal of arbitrary code insertion. Treat this as a **reviewer-observed Technical review concern** unless a current numbered rule directly applies; distinguish the review expectation from any proven XSS or code execution. Trace raw code fields in editors, REST/AJAX saves, imports and stored legacy data through inline styles/scripts, generated files or PHP execution. Check the whole path, not just whether an editor is visible.

Prefer structured controls with allowlisted properties and typed values, generating the required CSS/JS programmatically; use WordPress's existing CSS editing facilities where appropriate. Sanitizing arbitrary pasted code or adding `unfiltered_html` checks alone does not satisfy these messages' removal request. Ordinary generated block styles, bundled stylesheets and `wp_add_inline_style()` are not themselves proof of arbitrary insertion. Inspect generated CSS values and HTML `</style>` boundaries; HTML escaping/KSES and generic text sanitizers are not stylesheet validators. For raw script integrations, accept documented identifiers/settings instead of entire script bodies. Retest direct save/import paths and previously stored values, preserving valid structured styling.

## 4. Core files, paths, dependencies and installs

Never bootstrap WordPress from plugin endpoint files by `include/require wp-load.php`, `wp-config.php` or `wp-blog-header.php`. Use hooked PHP, AJAX, REST or rewrite endpoints. Other WP admin helper file loads **may** be legitimate; use `require_once` and consume the API immediately in authorized context (e.g. `upgrade.php` before `dbDelta`). Flag bare `include ABSPATH . 'wp-admin/includes/...';` for review; identify whether function exists without it.

Check paths resilient to relocated/renamed directories: `plugin_dir_path(__FILE__)`, `plugin_dir_url(__FILE__)`, `plugins_url(..., PLUGIN_MAIN_FILE)`, `wp_upload_dir()`, `admin_url()` and `rest_url()`. Hardcoded `plugins_url('my-plugin/...')`, direct `/wp-admin/admin-ajax.php` or `wp-content/plugins/slug` may be fragile. Avoid assuming filesystem location from folder name.

Check code that installs, activates, deactivates or upgrades **other** plugins. Users must explicitly initiate plugin activation/deactivation; no silent onboarding dependency installs. WordPress's `Requires Plugins` header is preferable where appropriate. Inspect admin capability checks for any user-initiated installation flow. Differentiate plugin self-deactivation on missing dependencies (can be warranted) from auto-activating third-party plugins.

## 5. Activation, storage, output buffers and runtime quality

Test on clean WordPress with `WP_DEBUG` and logs; require no fatals, warnings, notices, unexpected output, or unwanted calls on activation. Check dependency/version detection before use. Review DB schema with `$wpdb->prefix`, `$wpdb->get_charset_collate()` and `dbDelta()`'s specific SQL grammar: reviewers flagged `CREATE TABLE IF NOT EXISTS` sent to `dbDelta`. Check early scheduling causing translations-too-early notices, plus uninstall cleanup. Inspect deprecated PHP/WordPress functions and declared compatibility.

Inspect every `ob_start()` for matching `ob_get_clean`/`ob_end_clean`/`ob_end_flush` across **all paths**; count matching functions, not merely file-wide occurrences. Buffers scoped to request shutdown can be problematic. For PHP include/template files executing at top level, enforce a guarded entry point, generally `defined('ABSPATH') || exit;`, positioned after namespace and before executable code. Class-only files need judgment.

Protect cached invoices, customer PDFs and exports: `wp_upload_dir()` is commonly web-accessible, and a hashed filename does not authorize access. Prefer streaming documents through authenticated endpoints with per-order access checks, private temp storage with verified protection or short-lived secure downloads. Test direct HTTP access/directory listing. Validate uploads and file permissions. Inspect zip contents for temp/cache files with personal data, unsafe shell scripts, backup archives, suspicious executables and misplaced build artifacts.

## 6. Readme, assets, admin design, i18n and packaging

Match every **free** feature advertised in readme, plugin header, FAQ, tutorial screenshot and built admin copy to a real implementation that is enabled in the shipped plugin. Look for features written only to the database but never evaluated; empty functions; placeholders returning false/empty; "Pro" marketing indistinguishable from free; features only in external code. For absent features, either implement or remove/relabel claims. For screenshots/FAQ sections, don't infer semantics from filenames alone—read UI and flow.

Check required `Text Domain:` and literal domains in translation functions against the WordPress.org slug; this matters in compiled gettext JavaScript too. Do not report core/WooCommerce domains referenced legitimately by third-party packages as plugin-domain violations unless confirmed. Check unique prefixes for functions, classes, options, AJAX actions and REST namespaces. Inspect plugin-specific admin CSS registration to ensure `:root`, `img`, `input`, `textarea`, etc. are not leaked to every dashboard screen; restrict enqueue by screen and scope selectors. Only flag style reachability when confirmed.

For plugin-defined global names, use a distinctive prefix of at least four characters; avoid reserved leading `wp_`, `_` and `__`. Include constants, globals, shortcodes and setting names. A valid class prefix/namespace does not scope strings such as `wp_ajax_disable_google_font` or `installrequiredplugin`. Check PHP registrations and all source/compiled JS callers together. Do not rename core/third-party hooks or demand prefixes on every class method. `function_exists()` guards do not resolve collisions between unrelated plugins; distinguish legitimate shared-library guards. Cite [Common Issues: Prefixing](https://developer.wordpress.org/plugins/wordpress-org/common-issues/#prefixing) rather than inventing a numbered rule.

Flag spaces/trailing spaces and case-insensitive collisions in filenames, even deep in bundled vendor caches. Audit whether `.sh`, `.map`, `node_modules`, test fixtures or generated cache files are intended to ship; do **not** blanket ban `.map`—they can be harmless or useful as source references. Verify shipped and readable sources for minified builds; require correct redistribution licenses. `Trustpilot`/similar references deserve a targeted scan after the supplied reviewer emails, but should be called a **context-dependent branding/review-integrity concern**, not a generic prohibition on that word.

## 7. Applicability and severity policy

- **Blocker:** strong evidence of restricted local paid functionality, unauthorized sensitive data transmission, arbitrary public private-data access, directly accessible sensitive files, remote executable delivery prohibited by policy, or materially dishonest functionality claims.
- **High:** major security/review rejection risk with supported call path, e.g. missing capability for privileged operations, unsafe stored inputs/outputs, silent installation, widespread remote assets, broken privacy disclosure.
- **Medium:** real but localized potential reviewer finding, e.g. wrong domain, unsafe file-loading pattern, global dashboard styling, packaging filename problem, `dbDelta` syntax, unclosed buffer confirmed in an error path.
- **Low:** documentation/maintainability findings with limited reviewer impact and high confidence.
- **Confidence:** High = traced reachable flow or directly observable package defect; Medium = strong partial evidence; Low = suspicious pattern only. Never elevate confidence to match severity.

For regex-only findings, status `Needs manual verification` and appropriate low/medium confidence. Merge duplicates by root cause while listing **all impacted locations**; keep separate issues for different actual effects or remediations. Surface plausible false positives in a manual-review section without calling them confirmed policy violations.
